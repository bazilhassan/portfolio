Case study 01

OPIC3D · Uverse Digital · 2025–present App Store ↗

Building a spatial camera from scratch, then making it fast enough to ship.

Overview

OPIC3D captures spatial photos and video on iPhone and turns them into shareable 3D reels, with live streaming built in. The camera isn't a feature of the product — it is the product, so a regression in capture is a regression in the whole app.

My role

Lead iOS Developer. I lead a team of three engineers and own the camera system end to end: capture architecture, spatial and stereoscopic capture, camera controls, transcoding, and the LiveKit streaming layer.

The challenge

Spatial capture on iPhone means recording two synchronised eye streams, attaching the metadata Apple Vision Pro needs for playback, and transcoding the result so left and right eyes stay aligned. Every one of those steps adds processing time, and all of it sits between the user tapping record and the user seeing their result — a gap long enough to become a product problem, not just a technical one.

The app also needed several capture modes sharing one camera system — standard photo, standard video, spatial photo, spatial video — plus manual focus, autofocus and custom zoom, without the preview stalling every time a user switched between them.

Technical approach

  • Built the capture layer on AVFoundation around a single long-lived AVCaptureSession, batching input and output changes so mode switches reconfigure the session rather than tearing it down and rebuilding it.
  • Implemented stereoscopic capture with the spatial metadata required for correct Vision Pro playback, and a transcoding path that keeps left-eye and right-eye tracks synchronised.
  • Refactored capture-session reconfiguration to remove redundant work and keep transitions between camera modes responsive.
  • Built manual focus, autofocus, custom zoom and real-time preview as controls layered on that single session rather than as separate capture paths.
  • Shipped 2D live streaming on LiveKit with real-time audience comments and a custom in-stream keyboard, and contributed to the 3D streaming work.
  • Kept capture logic out of view controllers using MVVM and Clean Architecture, so the camera system can be reasoned about independently of the UI.

Key engineering decisions

  • One session, reconfigured — not a session per mode. Teardown latency lands at exactly the moment users expect the camera to be ready.
  • Capture logic isolated from the UI layer, so a change to camera controls can't destabilise the capture path.
  • Latency treated as a product requirement rather than a later optimisation, which is why the session refactor happened before launch instead of after.

Results

LiveProduction App Store release
Multi-modeUnified capture architecture

What I took from it

On camera work the expensive problems are almost never in the capture call itself — they're in state transitions and in everything that happens after the shutter. Mode switches, interruptions and post-capture processing are where a pipeline actually fails users, so that's where the architecture has to be deliberate.

Case study 02

Sibme · 3S Solutions · 2022–2025 App Store ↗

Making long-form classroom video reliable inside an established codebase.

Overview

Sibme is a video-coaching platform for educators: teachers record classroom sessions, upload them, and coaches leave time-stamped feedback on the footage. Recordings are long, often captured on school networks, and the app was already in production with an established user base.

My role

Senior iOS Developer in a 4-person iOS team. I delivered features end to end—from architecture and implementation through debugging, review and production support.

The challenge

Two problems ran in parallel. The media pipeline caused noticeable buffering on playback, which matters when a coach is scrubbing through an hour of classroom footage to leave feedback at specific timestamps. And audio recording had to survive the app being backgrounded — teachers don't sit watching a screen while they teach.

Both had to be solved inside a mature codebase with existing users, where a fix that destabilises playback is worse than the original problem.

Technical approach

  • Improved AVFoundation-based media playback and recording behavior, focusing on reliability for long-form classroom content.
  • Implemented reliable background audio handling so recordings continue correctly when the app isn't in the foreground.
  • Built file and folder management workflows, giving users structure over a growing library of recordings.
  • Implemented AI Tools, Insights, Coach chat and form-based workflows for coaching use cases.
  • Delivered notifications, onboarding improvements and production fixes without disrupting existing user workflows.
  • Reviewed code and supported junior developers to reduce regression risk.

Key engineering decisions

  • Fixed the media pipeline rather than adding buffering workarounds at the UI layer — the symptom was playback, but the cause was upstream.
  • Kept recording lifecycle behavior explicit so background transitions did not silently break long-running sessions.
  • Paired significant changes with careful review because, in an established codebase, the risk is often what a feature affects outside its own screen.

Technologies

Results

What I took from it

In a mature product, reliability improvements and new features cannot be treated as separate tracks. The best change solves the immediate user problem while leaving the surrounding code easier—not riskier—to evolve.

Case study 03

LUJO · Luxury lifestyle platform · UAE App Store ↗

Making location-dependent luxury discovery work across multiple booking products.

Overview

LUJO is a luxury lifestyle management and digital concierge platform. It gives users access to curated experiences, hotels, villas, dining, private and commercial flights, yacht charters, VIP event tickets and personalized concierge requests.

My role

Senior iOS Developer. I worked on the Events, Experiences, Yachts and Hotels modules, with responsibility for complex filters, booking flows and the asynchronous APIs that powered location-based discovery.

The challenge

The “Products by Region” flow used three dependent location levels: Region → Country → City. A selection at one level determined the available values and API requests for the next. That dependency had to behave consistently across four different product modules, each with its own catalogue, filters and booking journey.

The difficult part was not rendering three selectors. It was coordinating dependent network requests, keeping selection state consistent, and preventing older responses from producing incorrect filters as users moved quickly between regions, countries and cities.

Technical approach

  • Implemented the three-level regional discovery flow across Events, Experiences, Yachts and Hotels.
  • Coordinated dependent API operations using async/await, Grand Central Dispatch and OperationQueue according to the requirements of each workflow.
  • Managed selection, loading and response state so downstream Country and City data remained aligned with the user's current Region selection.
  • Integrated complex filters with module-specific product catalogues and booking paths.
  • Built and maintained interfaces using UIKit, Storyboards and Auto Layout, keeping the experience consistent across device sizes.

Key engineering decisions

  • Treated Region, Country and City as an explicit dependency chain rather than three independent filters.
  • Sequenced dependent operations so each request received the state produced by the level above it.
  • Applied the same state principles across multiple modules while preserving their individual product and booking requirements.

What I took from it

Dependent filters are state-management problems before they are UI problems. Making the hierarchy explicit—and controlling when each network operation can begin—keeps complex discovery experiences predictable as the product grows.
